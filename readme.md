# VoyahTune — форк

Твик штатной мультимедийной системы Voyah (Voyah Free / H97C) для Android 11. Управление режимами
езды и энергоустановки, светом, ключами CAN-шины, мультимедиа, приборкой и поведением OEM-процессов
через привилегированное системное приложение.

Проект работает **только на Android 11 (API 30)** и собран **без единой строки на Kotlin** — при
`minSdk = 30` и `targetSdk = 36` там только Java.

---

## Это форк

Основа — [nexron171/VoyahTune](https://github.com/nexron171/VoyahTune) (upstream `origin` =
`gitlab.com/openvoyah/voyahtune`). Ответственность за исходный проект остаётся у его автора; здесь
он поддерживается в своём виде.

Форк отталкивается от состояния upstream на коммите
`c8d0d1826487d0ea08fca30ecdfa946300718ba2` (v3.11.1 / ветка 4.0-rc1). Всё, что было в upstream **до**
этого коммита, перенесено; всё, что появилось **после** него, разбирается выборочно — часть
перенесена осознанно, часть отброшена и не переносится.

Важная деталь: перенос сделан переносом изменений, а не слиянием веток, поэтому `c8d0d18` **не
входит в историю этого репозитория**. Общий предок с upstream — `d2845c5`. Сейчас расхождение
выглядит так: 32 коммита upstream и 37 коммитов форка. Сравнивать нужно по содержимому, а не по
`git log`.

Отсюда важное: **это не апстрим-зеркало.** Здесь принимаются собственные решения, и некоторая
логика намеренно отличается от авторской. Список расхождений — в разделе
[«Чего нет и не планируется»](#чего-нет-и-не-планируется) и в разделе
[«Чем форк отличается»](#чем-форк-отличается).

## Устройство проекта

Это не обычное приложение: собирается из трёх сотрудничающих частей плюс инжектор, который
внедряется в OEM-процессы.

| Часть | Пакет | Роль |
|---|---|---|
| `Native/` | `ru.big.town.anative` | Системное **priv-app**. CAN-шина, JNI, сервисы, приёмники загрузки, хосты VirtualDisplay. Владеет всеми командами автомобилю. |
| `RestoreMode/` | `ru.big.town.restoremode` | Пользовательские **настройки** + `RestoreModeContentProvider` — источник истины по настройкам, который читает Native. |
| `Packaging/` | — | Источник истины для релиза: Frida-агенты, установщики, загрузочная обвязка, гварды. |
| `Releases/` | — | Только вывод сборки, целиком в `.gitignore`. Ничего не редактируется руками. |
| `Utils/` | — | Только для разработки: Frida-server, харнесс OEM-стабов, adb-логи. В релиз не попадает. |

### Границы между частями

- `RestoreMode` **не трогает автомобиль**. Он только пишет настройки в провайдер и отправляет
  Messenger-сообщения в `SetModesService`. Логики CAN там нет физически, и это закреплено гвардом
  `test_settings_only_ui.sh`.
- `Native` читает настройки через `content://ru.big.town.restoremode.restoremodecontentprovider/`
  и при недоступности провайдера падает обратно на свой кэш.
- Один канал команд — Messenger поверх биндинга, защищённого сигнатурным разрешением
  `ru.big.town.anative.permission.BIND_SET_MODES_SERVICE`. Публичные броадкасты для команд не
  используются.
- Порядок колонок в `RestoreModeContentProvider.query()` — **нагрузочный**: новые ключи только
  дописываются в конец, никогда не переставляются.

### Доступ к автомобилю

Три независимых пути, все в `Native`:

1. **Сырые CAN-кадры** — `CanSender` → JNI (`NativeCanBridge.send`) → `dlopen`/`dlsym` штатного
   `/system/lib64/libqg_hal.so`. Единственный нативный метод во всём проекте; имя класса закреплено,
   потому что на нём держится JNI-символ.
2. **Штатный OEM-Binder `com.qinggan.canbus.service`** — именованное состояние автомобиля
   (`OemVehicleStateTransport`, `HeadlightCanTransport`, `DriveModeCanTransport`). Работает через
   reflection, потому что API не входит в публичный SDK.
3. **OEM `CarSignalService`** — границы питания ACC, которые на части прошивок не отдаёт штатный
   `CarPowerManager`.

Читающая сторона — `CanBusEventHub` с одним набором callback'ов на все нужные сигналы.

### Frida-агенты

Восемь агентов закреплены в `Packaging/system/voyahtune-hook-manifest.json` вместе с целевым
процессом и SHA-256; девятый (`app_client.js`) инжектится по PID стороннего приложения и в
манифест не входит.

| Агент | Процесс |
|---|---|
| `vd_bypass.js` | `system_server` |
| `steeringwheelkeys.js` | `com.qinggan.keymanager.service` |
| `launcherdock.js` | `com.qinggan.app.launcher` |
| `multidisplay.js` | `com.qinggan.systemservice` |
| `apollo_tech.js` | `com.qinggan.app.vehiclesetting` |
| `keyboard_lock_en.js` | `com.qinggan.app.qgime` |
| `keyboard_ru.js` | `com.qinggan.app.qgime` |
| `instrumentcard.js` | `com.qinggan.instrumentcard` |

Перед каждой инъекцией `load.bin` сверяет SHA-256 агента и при расхождении закрывает набор
fail-closed. Успех подтверждается **маркером готовности, который агент сам печатает в stdout**, а не
кодом возврата инжектора.

### Компоненты `Native`

8 сервисов (`SetModesService` — основной канал команд и точка входа при загрузке,
`LightSensorService`, `WiperColdService`, `TripStatsService`, `BatteryHeatService`,
`NowPlayingService`, `MediaWidgetOverlayService`, `BackButtonService`), 3 приёмника
(`SetModesReceiverStatic` на `BOOT_COMPLETED`, `SetModesReceiverDynamic` для руля,
`SetModesConfigReceiver` под сигнатурным разрешением), 2 Activity для VirtualDisplay
(`SplitHostActivity`, `ClusterMediaHostActivity`) и провайдер `NowPlayingProvider`.

## Возможности

Настройки — один экран с боковым меню из десяти разделов. Отдельного домашнего экрана нет:
приложение настраивает машину, а не заменяет лаунчер.

| Раздел | Что делает |
|---|---|
| Быстрые действия | Поездка и её история, Power Hold, режим мойки, прогрев батареи, статус автомобиля, плитки приложений и split-пресетов, выбор источника медиа, порядок OEM-полок главного экрана |
| Настройки автомобиля | Режимы езды, энергоустановки, рекуперация, автосвет по датчику, сервисный режим дворников, звук пешеходов, фары на парковке, запоминание выбора |
| Приложения и разделение экрана | Сплиты с собственным соотношением, перетаскиваемый разделитель, полноэкранные приложения, per-app DPI, заморозка сторонних приложений, слоты системного дока |
| Apollo Tech | TLC, распознавание светофора и дорожных знаков напрямую через штатный CAN-Binder |
| Собственные команды | Свои 10-байтовые CAN-кадры |
| Кнопки на руле | Звёздочка, DVR, голос, трубка: короткое и долгое нажатие, в том числе пользовательский CAN |
| Другое | Перезагрузка, плавающие Назад/Home, права на установку, закрытие приложений, тема, переход в системные настройки, версия и диагностика |
| Приборка | Приложения и жест запуска в штатной медиа-области приборки, сортируемые карточки |
| Кастомные виджеты | Собственные карточки в штатных областях приборки |
| Производительность | Сбалансированный профиль с обратимым откатом |

Ключевые инварианты, которые нельзя нарушать случайно:

- **Всё по событию, никаких таймеров.** Периодические чтения `Settings`, подписки на CAN вне
  события и опрос по расписанию запрещены гвардами. Состояние толкается тем событием, которое его
  изменило.
- **Удаление остаётся за PackageManager.** Только `pm uninstall`, никогда `rm -rf` на
  `/data/user*` — иначе рассинхронизируется `/data_mirror` и Native падает в зиготе.
- **Один продукт, без flavor'ов.** Никаких `productFlavors`, `full`/`light` и `assembleFullRelease`.

## Сборка

Требования: **JDK 21**, Android SDK 36, **NDK 29.0.14206865** с **CMake 3.31.6**, Gradle 9.5
(через wrapper), AGP 9.3.0, Node с `npx` — релизная минификация зовёт закреплённый
`esbuild@0.25.0`.

Полный релиз — в `Releases/build/VoyahTune-<версия>/` плюс zip в `Releases/dist/`:

```bash
./make_release.sh 3.9.0                   # принимает и "3.9.0", и "v3.9.0"
./make_release.sh 3.9.0 --no-build        # переиспользовать уже собранные APK
./make_release.sh 3.9.0 --no-zip
```

Отдельно:

```bash
cd Native     && ./gradlew assembleRelease
cd RestoreMode && ./gradlew assembleRelease
```

Релиз подписывается отладочным ключом — keystore не нужен. В релизной сборке включены R8 и
shrinkResources. `versionCode` / `versionName` **не меняются** скриптом релиза: их нужно поднять
руками в `Native/app/build.gradle.kts` и `RestoreMode/app/build.gradle.kts`.

Правки в `Packaging/inject/*.js` требуют перегенерации манифеста хуков:

```bash
./Packaging/update_hook_manifest.sh
```

## Установка

Нужен `adb root` и записываемый `/system`, и **две перезагрузки**: приёмник `BOOT_COMPLETED`
регистрируется только после установки, а сервис стартует на следующей загрузке.

В релизе есть `install.sh` (macOS/Linux) и `install.bat` (Windows), плюс отдельный
`install-yandex-dns` для DNS-overlay. Подробная инструкция — в `README.txt` внутри архива.

Для разработки: `Native/push-priv-app.sh` требует эмулятор, запущенный с `-writable-system`
(рецепт есть в комментарии `Native/run_emul.sh`). `Native/run_main.sh` шлёт
`com.qinggan.intent.QINGGAN_BOOT_COMPLETE`, чтобы поднять сервис без перезагрузки.
`Native/readlog.sh <имя>` снимает `adb logcat`.

## Чего нет и не планируется

Это осознанные решения, а не недоработка.

### Голосовое управление

В upstream есть голосовой помощник: офлайн-распознавание речи на Vosk/Zipformer2 + DeepFilterNet3,
разбор фраз детерминированным матчером и большая таблица голосовых команд. **Здесь этого нет и
добавлять не планируется.**

Причина архитектурная, а не идеологическая: у голосового помощника должен быть постоянно
резидентный весищий процесс с моделями на сотни мегабайт внутри системного priv-app, отдельный
микрофонный foreground-сервис и новый канал команд. Для настроек автомобиля это неоправданно —
функции, ради которых берут эту сборку, достигаются кнопками на руле и разделами настроек.

### Встроенные живые виджеты и отдельный домашний экран

В upstream приложение — лаунчер: отдельный Activity-главная с сеткой виджетов, где плитка
приложения рендерит живое приложение внутри себя через `Surface` + `VirtualDisplay`, с кнопкой
«открыть в полный экран». **Здесь этого нет и не будет.**

Причина та же: настройка не должна заменять собой лаунчер. Плитки в «Быстрых действиях»
остались — они запускают приложение или готовый сплит, то есть работают как ярлыки, а не как
встроенный виджет с собственной задачей и Surface. Это разные вещи, и смешивать их не стоит.

### Остальное, что не переносится

- **Команды голоса для сидений, окон, люка и шторки.** Обратный реверс полей OEM без проверки на
  автомобиле: документ самого автора прямо говорит, что на ГУ это не проверялось, а наличие поля
  в API не гарантирует поддержку комплектацией.
- **Уставка SREV и оценка объёма топлива для дозаправки.** У автора там зафиксирован
  неподтверждённый на машине баг, при котором «топливо 25» переключало режим, но не меняло
  уровень.
- **Параллельный загрузчик хуков с супервизором воркеров.** Рефакторинг из ~230 строк в
  `load.bin`, у которого нет подтверждённого выигрыша: собственный чек-лист автора оставляет
  замер на автомобиле **неотмеченным**, а последующий замер касается только холодной загрузки, не
  resume после suspend. Рефакторинг требует удалить часть наших собственных гвардов
  (порядок MD-before-VD, `WATCHDOG_CYCLE_SECONDS=5`) и заменяет последовательный `frida-inject` на
  до четырёх параллельных attach'ей в OEM-процессы. Взамен из этого взяты только реальные
  исправления, а не перестройка.

### Чего нет в upstream, но есть здесь

- Один продукт вместо сборки full/light с Gradle-вариантом.
- Собственный алгоритм восстановления режимов после двери и первого Drive — устойчивее авторского.
- Модель подтверждения инъекции руля: успех только по маркеру из stdout агента, плюс re-check
  identity после fork.
- Экранирование разделителей записей `|` под семантику mksh, и права на `/data/local*` для UID
  агента. Оба бага были и здесь, оба воспроизведены и закрыты.
- Джокеры `import-` в MediaSession, чтобы сторонние плееры попадали в штатную медиа-карточку.
- Транспорт Spotify через штатную OEM-модель медиа.

## Чем форк отличается

Коротко: у формы другая архитектура, а не просто другая версия.

| | Upstream | Здесь |
|---|---|---|
| Стой | Полный и облегчённый | Один продукт, без flavor'ов |
| Главный экран | Лаунчер с живыми виджетами | Раздел «Быстрые действия» внутри настроек |
| Восстановление режимов | Дверь + первый Drive, не дополнено у нас | Собственный алгоритм, устойчивее на практике |
| Голос | Zipformer2 + DeepFilterNet3, ~100 МБ моделей | Нет |
| Загрузчик | Последовательный, с супервизором воркеров | Последовательный, с усиленной проверкой целостности |
| Интерфейс | Отдельные экраны приложения и виджетов | Один экран настроек с боковым меню |
